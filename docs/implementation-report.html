mcproxy implementation

A local MCP proxy with one endpoint and stable bearer token per provider profile. Upstream credentials and OAuth refresh stay in the daemon. Tools, resources, prompts, schemas, results, and protocol errors retain their original names and content.

Provider configuration → authenticated profile → /mcps/linear/profile1
A second profile has separate credentials, token, sessions, and endpoint.

Implemented

AreaBehavior
ProvidersStreamable HTTP upstreams and local stdio commands. Provider setup, profile management, connection testing, deletion, and token rotation.
AuthenticationNo authentication, bearer tokens, custom HTTP headers, stdio environment variables, or OAuth. OAuth discovery, registration or configured client credentials, PKCE, callback state validation, encrypted persistence, and serialized refresh.
IsolationEvery downstream request authenticates against its profile. Each downstream session gets a separate upstream transport. Credential changes, deletion, and rotation close sessions. Stale OAuth responses cannot overwrite changed credentials.
StorageSQLite through Drizzle, transactional migrations, AES-256-GCM encryption for upstream secrets, and hashes of downstream tokens. The encryption key and state directory have owner-only permissions.
InterfaceReact, TanStack Router, Query and Form, Vite, Tailwind, and shadcn. Dense dark provider/profile workspace, one-time token reveal, copy controls, OAuth connection, connection testing, and confirmation for destructive actions.
RuntimeTypeScript and Effect 4.0.6. Node 22 and pnpm 11. The daemon binds to 127.0.0.1:7433. Production serves the built UI; Vite development uses 127.0.0.1:5173.

Run locally

pnpm install
pnpm dev

For the built application, run pnpm build followed by pnpm start. The process runs in the foreground.

Verification

Full workspace typechecks and production builds pass. All 22 tests pass: 13 backend tests and 9 frontend tests. Frozen-lockfile installation also passes.

  • HTTP and stdio discovery, tool calls, resources, prompts, errors, token enforcement, profile isolation, and process cleanup.
  • OAuth state validation, PKCE, refresh after restart, profile replacement during token exchange, and denial handling, using a deterministic local fixture.
  • Server requests during HTTP initialization and concurrent POST calls, message delivery before GET opens, and bounded queue overflow.
  • Frontend form payloads and validation, API failures, and required management headers. Vite's development proxy was checked for successful management calls and foreign-origin rejection.

Recorded demos

Four local MP4 recordings accompany the source. They show HTTP provider setup with two profiles, simulated OAuth in the management UI, the separate simulated consent tab, and stdio provider setup. Recordings use disposable daemon state and synthetic credentials. The OAuth provider is a local fixture, not a real external account.

Current limits

  • macOS was verified. Linux and Windows filesystem boundaries are present but those platforms were not tested.
  • Legacy HTTP+SSE transport and event-ID replay or resumption are not implemented. HTTP upstreams use single-message Streamable HTTP.
  • Unsolicited messages require a downstream GET SSE stream. During gaps, each session queues up to 128 messages or 1 MiB. Overflow closes the session. Messages already handed to a disconnected stream may be lost.
  • Stdio callbacks require GET after initialization. A stdio server that requires a client callback during initialization is unsupported. MCP content is preserved within these transport limits.
  • OAuth scope escalation requires reconnecting with the requested scopes. Real provider interoperability still needs testing with actual accounts.
  • Keychain integration, login startup, and tracking detached subprocess grandchildren are not implemented.
  • The production JavaScript bundle is approximately 679 kB, or 205 kB gzip. Vite reports its bundle-size warning.
